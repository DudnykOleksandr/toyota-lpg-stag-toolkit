Статус (2026-09-29): **етапи 0–3 і простий експорт (5) написані в `android/`, перевірені на симуляторі;
в авто ще не перевірялись.** Пріоритети власника: ① дашборд, ② запис логів для аналізу (підсос
повітря, брудний MAF). Тому живий дашборд з етапу 6 — головний екран уже зараз. Телефон: Xiaomi
(MIUI), Android 13, APK ставиться вручну.

## Мета

Телефон сам записує поїздки через ELM327 — без ноутбука. Файли сумісні з `logger/analyze.py`.
Власник скидає їх у репу (`logs/`), далі — звіт про здоров'я двигуна й систем з порівнянням з
еталонним записом.

## Принципи

- **Тільки читання.** Жодного стирання кодів (сервіс 04) і жодних записів в ECU. У коді — один
  білий список дозволених команд.
- **Формат файлів той самий, що в ноут-логері** (`elm_YYYYMMDD_HHMMSS.csv` + `.log` +
  `.meta.json` + `.health.json`), щоб аналізатор працював без змін.
- **Мінімум взаємодії в дорозі:** автостарт, великі кнопки-позначки.

## Архітектура

| Шар | Що | Звідки |
|---|---|---|
| Транспорт | Bluetooth Classic SPP до `OBDII` (PIN 1234); TCP-транспорт для симулятора | новий код |
| Протокол ELM | ініціалізація, мульти-PID в один CAN-кадр, адресація 7E0/7E1, розбір кадрів, автоперепідключення | порт `logger/elm327.py` |
| Каталог PID | формули стандартних PID, швидкі/повільні групи, `ATRV`, ATF `21D9` | порт з `logger/elm_logger.py` |
| Знімок стану | MIL, коди (03/07/0A), готовність моніторів, пробіг/час з моменту стирання, VIN/CALID, режим 06 (пропуски по циліндрах) | порт `logger/obd_health.py` |
| Запис | foreground service, CSV з `flush` на кожен рядок, `.log`, `.meta.json`, `.health.json` | формат як у `logs/` |
| UI | Jetpack Compose: статус з'єднання, позначки, режим «Перевірка здоров'я», список поїздок, «Поділитися» | новий код |

**Стек:** Kotlin, Jetpack Compose, `minSdk 31`, `targetSdk 33` (Android 13). Без сторонніх
OBD-бібліотек — власний драйвер, як у Python, бо він уже перевірений на цьому авто
(ELM327 v1.5, ISO 15765-4 CAN 11/500).

## Етапи

### Етап 0. Середовище
- Android SDK + Gradle на ПК. Встановлений JDK 26 для Android Gradle Plugin не підходить →
  JDK 21 (або Android Studio з вбудованим JBR).
- Порожній проєкт у `android/`, збирання debug APK.
- **Готово:** APK збирається, ставиться на телефон і відкривається.

### Етап 1. Зв'язок з ELM
- Дозволи Bluetooth Android 12+ (`BLUETOOTH_CONNECT`), вибір спареного `OBDII`, ініціалізація,
  список підтримуваних PID.
- Тестовий режим: TCP-підключення до `logger/sim.py` (у `sim.py` додати TCP-режим — мала правка).
- **Готово:** з авто на екрані версія ELM, протокол CAN 11/500 і той самий набір PID, що в
  `logs/elm_20260928_130033.meta.json`.

### Етап 2. Запис поїздки
- Foreground service з нотифікацією; опитування швидких і повільних груп; ті самі колонки CSV;
  `.log` з подіями.
- Автоперепідключення після обриву BT у той самий файл; зупинка вручну або коли ECU мовчить
  N хвилин.
- **Готово:** 30 хв поїздки з вимкненим екраном, обрив BT переживається, `analyze.py` будує звіт
  з цього CSV без правок.

### Етап 3. Позначки й знімок стану
- Кнопки: газ / бензин / A/C увімк. / A/C вимк. / траса / місто / холості / довільна позначка →
  колонка `marker` (як клавіші `g b a s h c i m` у ноут-логері).
- Знімок стану на початку й у кінці → `.health.json`.
- **Готово:** позначки й розділ «Стан ECU» з'являються у звіті аналізатора.

### Етап 4. Режим «Перевірка здоров'я»
- Покроковий сценарій з таймерами: холодний старт → 2 хв холостих → 15–20 хв звичайної їзди →
  один розгін у пол (за бажанням) → холості з A/C і без.
- Позначки кроків автоматично; у `.meta.json` — `"type": "health_check"`.
- **Готово:** одна кнопка — далі додаток веде сам.

### Етап 5. Експорт
- Список записів; «Поділитися» (Google Drive, Telegram…) архівом з усіма файлами поїздки.
- Автопуш у GitHub свідомо не робимо (токен на телефоні).
- **Готово:** відправити поїздку в одне торкання → файли кладуться в `logs/`.

### Етап 6 (пізніше, за бажанням)
Живий дашборд (ОЖ, ATF, напруга, трими) і попередження: ОЖ > 105 °C, ATF > 110 °C,
зарядка < 13.2 В.

## Звіт про здоров'я (на боці репи)

- Новий `logger/health_report.py` поверх `analyze.py`: остання «Перевірка здоров'я» проти
  еталонної та попередніх.
- Тренди: STFT+LTFT по режимах, час прогріву, стабільність ОЖ, лямбда й каталізатор
  (B1S2, режим 06), пропуски по циліндрах, напруга спокою й зарядки, температура ATF, коди
  (у т.ч. очікувані).
- Кожен пункт: «норма / змінилось / перевірити руками» + що саме змінилось.
- **Еталон:** перший запис після чистки MAF і заміни повітряного фільтра.

Чого телефонні логи не покажуть: стан Stag (тиск газу, Г, карта D — лише AC STAG на ноуті),
механіку (компресія, масло, знос, ходова, гальма). Газ/бензин ECU не бачить — лише з позначок.

## Ризики

| Ризик | Рішення |
|---|---|
| Android вбиває фоновий процес | foreground service + виключення з оптимізації батареї; перевірити на конкретному телефоні |
| Обриви BT у клона ELM | автоперепідключення в той самий файл |
| ATF `21D9` (байт 4 − 40) — поки кандидат | підтвердити прогрівом (росте разом з ОЖ, повільніше); до того в UI «експериментальне» |
| ELM тримає одне з'єднання | повідомлення «ELM зайнятий — відключи ноут / інший додаток» |
| Газ/бензин не видно з OBD | кнопки-позначки; без них палива не порівнюються |

## Відкриті питання до старту

1. Модель телефона (агресивність керування фоновими процесами).
2. Встановлення APK вручну («невідомі джерела») — ок?
3. Чи є на телефоні інший OBD-додаток (конфлікт за ELM).
4. ATF: підтвердити окремим прогрівом з ноутом чи одразу в додатку як експериментальне.

## Обсяг

Етапи 0–3 — основа (1–2 сесії), етапи 4–5 — ще одна; звіт про здоров'я — паралельно, окремим
скриптом.
